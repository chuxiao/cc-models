## 0. 形态声明

产物形态：桌面 App（既有应用的产品名改名迭代）。
章节裁剪推导：界面规格——适用（改名即界面与打包产物文案变更，引用冻结稿并声明其产品名以本需求为准）；数据字典——不设（零数据变更，配置格式与目录语义沿用既有设计）。

## 1. 背景与目标

- 解决什么问题：产品名定名时为「CC Model」，需求方现定名「CC Models」——全部用户可见面仍显示旧名，与需求方的产品命名不一致。
- 给谁用：需求方本人（该应用的唯一用户）。
- 成功判断标准：最终用户在全部显示面（打包产物名、窗口标题、退出菜单项、应用菜单标题、欢迎窗、通知标题、配置损坏弹窗、README）看到的产品名均为「CC Models」；应用全部功能行为与既有完全一致。

## 2. 功能清单

### R1 产品名全局替换

1. **定位：** 把全部显示面的产品名从「CC Model」统一替换为「CC Models」。
2. **触发与输入：** 应用构建与运行即生效；无用户操作。
3. **执行要点：**
   - 显示面触点全量替换：打包产物名（CC Models.app 及脚本内引用）、系统层显示名（应用名与显示名）、偏好窗口标题（「CC Models 设置」）、退出菜单项（「退出 CC Models」）、欢迎窗（窗口 title、标题 Text、正文 Text 三处）、通知标题、配置损坏弹窗（「CC Models 配置文件已损坏」）、应用菜单标题。
   - 测试断言中钉住上述文案的逐字断言同步更新（改名是唯一授权的文案变更；其余逐字文案——通知正文、「（默认）」徽标、菜单结构——零改动）。
   - README 全部「CC Model」替换为「CC Models」。
4. **出口表：** 单一出口——全部显示面呈现 CC Models。
5. **流程图：** 不配图——机械替换，无分支。
6. **本次不做：** 见 §3 第 1–3 条。

## 3. 明确不做

1. 不改系统层应用标识（com.ccmodel.app）——因为改标识会使既有登录项登记失效、需要重新登记，且该标识对最终用户不可见。
2. 不改配置目录名与构建包名/可执行名（cc-model / cc_model / ccmodel）——因为改名需要数据迁移与打包脚本连锁改动，对最终用户不可见，收益为零。
3. 不改仓库名与路径——因为那是外部系统操作（宿主目录），不在本应用交付物范围内。
4. 不改已归档文档——因为归档冻结，历史文档记录的是当时的产品名。

## 4. 关键决策记录

| 决策 | 一句话结论 | 拍板状态 | 影响功能项 |
|------|-----------|---------|-----------|
| D1 改名范围 | 显示面全改，内部标识不动 | 已裁决（2026-11-06，decisions.md 首条，待需求方随确认一并复核） | R1 |

**D1 改名范围**
1. 候选：只改窗口与菜单等应用内文案；显示面全改（含打包产物名与系统显示名）；全量改（含内部标识）。
2. 选择：显示面全改，内部标识不动。
3. 依据：需求方原话「软件名改为 CC Models」指向用户可见的产品名；内部标识改动的成本（登录项重登记、数据迁移、构建链改动）不产生用户可见收益。依据原句：「内部标识改动带来登录项重登记与数据迁移成本而用户不可见」。
4. 代价：系统层应用标识与显示名短期不一致——macOS 菜单栏与窗口标题以显示名为准（显示名已改），应用标识仅影响系统内部分辨，用户不可感知。**登录项副作用**：产物名改为 CC Models.app 即改变 /Applications 安装路径，既有登录项登记随之失效，重装后需在偏好中重新登记一次——该成本由显示面改名本身引起，与是否保留应用标识无关。保留标识的真实收益是免除配置数据迁移与构建链改动。成本量级：可忽略（纯文案替换 + 断言同步）。

**留给构建者的部分**

- 替换的执行方式（逐处编辑或脚本辅助替换）与替换后的全量校验手段（如改名范围内检索「CC Model」残留），边界：不遗漏显示面触点、不误伤内部标识；为什么交构建者：机械操作，方式自便。

## 5. 关键约束与可行性风险

- 行为零变更红线：143 条既有测试中，仅钉住应用名文案的断言随改名同步更新，其余零改动全绿。
- 逐字文案红线的范围裁定：应用名相关文案随本需求更新（decisions.md 条目 2）；通知正文、「（默认）」徽标、菜单结构零改动。
- 打包脚本的应用名常量与 plist 槽位是同一值的多处出现（含头注释与安装提示），须一致替换。
- 成本量级：单人约 0.5 小时（机械替换 + 断言同步 + 全量测试）。
